# 内存耗尽假死 → 硬重启干碎引导 → 深夜 Ventoy 抢救 → 顺手造了套开机自愈系统

> **日期**: 2026-09-18 ~ 09-19（深夜特供）
> **机器**: HP ProBook 4430s（i5-2450M / 7.7G RAM / 机械盘）
> **系统**: Ubuntu 24.04（kernel 6.17）+ Windows 双系统，BIOS/Legacy 模式
> **问题**: 白天机器假死 → 硬重启 → 重启后连系统都进不去了 → 用 Ventoy U盘深夜抢救
> **结局**: 机器救回来了，还顺手部署了一套"防/守/修/救"四层开机自愈系统

---

## 一、案情还原：机器是怎么死的

白天跑着 openclaw + codebase 索引（多个 agent 并行）这类重负载，机器卡死了。硬重启之后——GRUB 直接不认了，怎么都进不去系统。用 Ubuntu live U盘（Ventoy）启动，装了个 SSH 从内网另一台 Windows 远程操作，连夜抢救。

**根因侦查用的就是"临终遗言"**——`journalctl -b -1`（上一次开机的日志），死状清清楚楚：

| 时间（凌晨） | 日志证据 | 说明 |
|---|---|---|
| 01:28:36 | `sshd: error: no more sessions` 连刷数十秒 | **内存耗尽的指纹**：sshd fork 不出新会话了 |
| 01:51:21 | `systemd-journald: Under memory pressure, flushing caches` | 内核正式宣告内存高压 |
| 01:52:18 | `tailscaled: subscriber slow (14m2.49s elapsed)` | 进程卡到 14 分钟才响应一次——系统在抽搐 |
| 之后 | 日志戛然而止 | 彻底假死，硬重启，引导受伤 |

### 排除法断案

| 嫌疑人 | 证据 | 结论 |
|---|---|---|
| 硬盘坏了？ | 内核日志无 `ata* error`、无 `ext4-fs error` | 无罪 |
| OOM killer 没干活？ | 日志里根本没有 `Out of memory: Killed process` | 无罪，但它也已经被挤到跑不动了 |
| 内存+swap 耗尽 | 7.7G 内存 + 4G swap 被并行 agent 重负载打穿，进入疯狂换页死锁区 | **真凶** |

**为什么 systemd-oomd（Ubuntu 自带的内存保镖）没接住**：它只监控配置了 `ManagedOOMMemoryPressure` 的 cgroup（用户会话切片），而且它是普通用户态进程——系统抽搐到后期，连它自己都被换页压力饿死了。保镖和雇主一起晕倒，约等于没有保镖。

## 二、深夜抢救实录（Ventoy live + chroot 重装 GRUB）

BIOS/Legacy 双系统盘，`lsblk -f` 认地形：`sda1` = Windows「系统保留」NTFS 引导分区，`sda2` = ext4 根分区。标准修复流程：

```bash
# 在 live 系统里，以下按顺序执行
sudo fsck -y /dev/sda2              # 先修文件系统（硬重启留下的脏状态）
sudo mount /dev/sda2 /mnt
for i in /dev /dev/pts /proc /sys /run; do sudo mount --bind $i /mnt$i; done
sudo chroot /mnt
grub-install /dev/sda               # ⚠️ BIOS 模式下目标是整盘，不带数字！
update-grub
exit
sudo umount -R /mnt
sudo reboot
```

**BIOS 模式的关键细节**：`grub-install /dev/sda` 写的是整盘 MBR（引导代码 + 分区表），不是分区。写成 `sda1`/`sda2` 就是给 Windows 引导分区/根分区头部写垃圾。

## 三、顺手造的自愈系统（本目录 `selfheal/`）

抢救完复盘：这次是"假死 → 硬重启 → 引导碎"三连，那就在每一环上放一个守卫。四层防御：

| 层 | 防什么 | 靠什么 |
|---|---|---|
| **防** 防假死 | 内存耗尽抽死 | swap 8G + swappiness=30 + zswap（机械盘收益大）+ **earlyoom**（独立于 oomd 的第二保镖，内存将尽先杀大户） |
| **守** 守卡死 | 真卡死了没人管 | **压力哨兵**：内存 full 停滞连续 6 分钟 ≥90% → 强制重启自救；硬件看门狗（iTCO）兜底 |
| **修** 修开机 | 硬重启留下的脏文件系统 | fstab `passno=1` 开机自动 fsck（Ubuntu 内置）+ 每 30 次挂载/每月深度检查 |
| **救** 救引导 | GRUB/MBR 被覆盖 | MBR 备份 + `repair-boot.sh` 一键救援脚本（放 Ventoy U盘） |

外加**熔断器**：连续 3 次异常开机 → 自动停用看门狗和哨兵（防重启循环），人工修复后正常重启一次自动恢复。

### 诚实的边界

"GRUB 被覆盖"这种引导层故障**不可能系统内自愈**——系统没起来，脚本没机会跑，这是物理极限。所以引导层的答案是"备份 + 一键救援"，把深夜手敲 8 条命令压缩成 U盘里跑一个脚本。

### 部署

```bash
sudo bash selfheal/install-selfheal.sh   # 幂等，可重复跑
sudo reboot                              # 让 zswap 生效 + 开机守卫首航
# 验证：
cat /sys/module/zswap/parameters/enabled # 应为 Y
/usr/local/sbin/selfheal.sh status       # 心跳/熔断状态速览
```

脚本清单：

| 文件 | 作用 |
|---|---|
| `selfheal/install-selfheal.sh` | 一键安装器（8 步，全部幂等） |
| `selfheal/selfheal.sh` | 守护本体：心跳/压力哨兵/开机守卫/关机标记/GRUB 备份 |
| `selfheal/repair-boot.sh` | Ventoy U盘救援脚本（fsck / chroot 重装 GRUB / 恢复 MBR 三选一） |
| `selfheal/systemd/` | 6 个 systemd 单元（心跳 timer、开机守卫、关机标记、月度备份） |

状态与留痕都在 `/var/lib/selfheal/`：`boot-history.log`（每次开机一行：正常/异常、fsck 修没修过东西）、`mbr-latest.img`（MBR 备份，救命的）。

## 四、本次踩坑清单（每一条都是真金白银踩出来的）

| # | 坑 | 根因 | 解法 |
|---|---|---|---|
| 1 | 假死后日志只剩 `sshd: no more sessions` 刷屏 | 这是内存耗尽的指纹，不是 ssh 的 bug | 看到 `no more sessions` 刷屏 + journald `Under memory pressure` = 查内存，别查 ssh |
| 2 | systemd-oomd 开着却眼睁睁看系统抽死 | 只管自家 cgroup；抽搐后期自己也饿死 | 补 earlyoom 做独立保镖 + 压力哨兵兜底 |
| 3 | live 系统里新建的用户 `sudo` 报 `not in the sudoers file` | live 会话自带用户才有 sudo，新装用户没加组 | 在 live 桌面终端跑 `sudo adduser <user> sudo`，然后重新 SSH 登录生效 |
| 4 | BIOS 双系统机 `grub-install` 装哪儿？ | 写分区=毁 Windows 引导区/根分区头 | 写**整盘** `/dev/sda`（不带数字）；`系统保留` NTFS 分区分毫不动 |
| 5 | U盘挂载后文件管理器/普通用户看不见 | 用 sudo 挂载 → 挂到 `/media/root/`（root 家目录，700 权限） | 卸掉后以自己身份 `udisksctl mount -b /dev/sdb1` → 挂到 `/media/<user>/`；桌面正常插拔会自动挂 |
| 6 | swap 扩容时 `swapoff` 可能直接把机器拖死 | swapoff 要把换出数据全读回内存 | 红线：`available > swap used` 才动手（本例 7.7G 内存 + swap 仅用 12K，秒过） |
| 7 | `systemctl list-timers selfheal*` 显示 0 个定时器 | shell 把 `selfheal*` 展开成了当前目录的 `selfheal.sh`，systemctl 收到的是个文件名 | 查询单元名加引号：`systemctl list-timers 'selfheal*'` |
| 8 | 安装器误报 `passno=during` | awk 把 fstab 注释行 `# / was on /dev/sda2 during...` 的 `/` 当成了挂载点 | awk 加 `!/^#/` 过滤注释：`awk '!/^#/ && $2=="/" {print $6}' /etc/fstab` |

## 五、下次再遇到，三步走

1. **机器卡死先别按电源**：`Alt+SysRq(PrtSc)` 依次按 `R E I S U B`（每键隔 2 秒）——安全重启，sysrq=176 允许 sync/重挂载/重启，比硬断电温柔得多，还能避免文件系统受伤。
2. **起来了查死因**：`journalctl -b -1 -p err` + `journalctl -b -1 | tail`，对着第一节那张表认死法。
3. **进不去了上 U盘**：Ventoy 启动 → live 终端 → `sudo bash repair-boot.sh` → 菜单 3（重装 GRUB）/ 菜单 4（恢复 MBR）/ 菜单 2（fsck）。
